# 自律型週次ポスト改善ループ 要件定義

**作成日**: 2026-06-08
**ステータス**: ドラフト（要レビュー）

---

## 1. 背景と目的

現状、`analyzeAndImprove()`（`src/lib/self-improve.ts`）は「過去の投稿実績を分析 → プロンプトを改善」までを1ステップで行い、`/api/generate` ボタン押下のたびに実行されている。分析結果は `prompt_configs` / `prompt_config_history` に直接反映されるのみで、**「何をどう分析し、なぜそのプロンプトに改善したのか」という過程が人間に見える形で残らない**。

本要件は、以下を満たす「自律ループ」を定義する。

> 投稿を分析 → その分析レポートを読んで次週の投稿を作る → さらにそのポストを分析する … というサイクルを、人間の最終承認を残しつつ自律的に回す。

### スコープ外（今回は扱わない）
- 完全自動公開（人間レビューを廃止すること）
- Slack等の外部通知連携の実装（設計のみ言及）

---

## 2. ループ全体像

```
┌────────────────────────────────────────────────────────────┐
│                                                              │
│   ① メトリクス収集（既存 /api/metrics/fetch を流用）           │
│        ↓                                                     │
│   ② 週次分析レポート生成（新規）                               │
│      - 直近の公開済み投稿 + メトリクスを構造化分析             │
│      - weekly_reports に保存（人間が読める形で永続化）         │
│        ↓                                                     │
│   ③ プロンプト改善（既存 self-improve を「レポートを読んで     │
│      改善する」形に再構成）                                    │
│        ↓                                                     │
│   ④ 次週ポスト生成（既存 /api/generate のロジックを流用）       │
│      - status = 'draft' で保存                                │
│        ↓                                                     │
│   ⑤ 人間レビュー（既存フロー: draft → review → ready）★必須   │
│        ↓                                                     │
│   ⑥ スケジュール公開（既存 /api/cron/publish）                │
│        ↓                                                     │
│   ① に戻る（次サイクルの分析対象になる）                       │
└────────────────────────────────────────────────────────────┘
```

**人間が関わるのは⑤のみ**。①〜④は1回のトリガーで自動的に連鎖実行される。

---

## 3. 確定した設計方針（ブレインストーミングでの決定事項）

| 論点 | 決定 |
|---|---|
| 自律度 | 投稿前レビューは必須のまま維持。①〜④（分析・レポート生成・プロンプト改善・投稿生成）を自動連鎖させ、人間は「承認」だけ行う |
| 分析レポートの用途 | (a) 次回生成時にAIへの入力として渡す、(b) 人間向けダッシュボードに表示する。両方を満たす構造で保存する |
| 実行トリガー | 当面はダッシュボードの「ループを1サイクル実行」ボタンによる手動トリガー。動作が安定した後にCron化できるよう、ループ本体はトリガー方式に依存しない関数として設計する |

---

## 4. 新規データモデル

### 4.1 `weekly_reports`（週次分析レポート）

AIが生成した分析結果を構造化データと自然言語の両方で保存し、「人間が読む」「次回生成時にAIへ読ませる」の両方に使えるようにする。

```sql
CREATE TABLE weekly_reports (
  id              uuid PK,
  account_id      uuid FK → accounts,
  period_start    timestamptz,   -- 分析対象期間の開始
  period_end      timestamptz,   -- 分析対象期間の終了
  analyzed_post_count integer,   -- 分析対象になった投稿数
  metrics_summary jsonb,         -- 集計値（合計/平均インプレッション・いいね等）
  highlights      jsonb,         -- 高評価/低評価だった投稿とその要因（構造化）
  insights        text,          -- 自然言語の分析サマリー（人間向け表示・AI入力の両方に使用）
  next_actions    text,          -- 次週への改善提案（プロンプト改善のインプットになる）
  created_at      timestamptz
);
```

- `insights` / `next_actions` をプロンプト改善ステップにそのまま渡せる構造にする（後述）。
- `metrics_summary` / `highlights` はダッシュボードでのグラフ・表表示に使う。

### 4.2 `loop_runs`（ループ実行履歴）

1サイクルの実行結果を記録し、ダッシュボードで「いつ・どのアカウントで・何が起きたか」を追跡できるようにする。将来Cron化した際の冪等性チェック・リトライ判断にも使える。

```sql
CREATE TABLE loop_runs (
  id              uuid PK,
  account_id      uuid FK → accounts,
  status          text,    -- 'running' | 'completed' | 'failed'
  triggered_by    text,    -- 'manual' | 'cron'
  report_id       uuid FK → weekly_reports (nullable),
  generated_post_ids uuid[],  -- このサイクルで生成された投稿のID
  error_message   text,
  started_at      timestamptz,
  completed_at    timestamptz
);
```

- 既存の `prompt_config_history` と組み合わせることで「このサイクルでレポートが生成され→プロンプトがこう変わり→この投稿群が生まれた」という一連の流れを追跡可能にする。

## 5. 処理フローの詳細設計

### 5.1 ステップ②: 週次分析レポート生成（新規関数 `generateWeeklyReport`）

- **入力**: `accountId`, 分析対象期間（デフォルト直近7日 or 直近の公開済み投稿）
- **処理**:
  1. 対象期間の `published` 投稿 + `post_metrics` を取得
  2. メトリクスが揃っている投稿が一定数（既存の閾値=3件を踏襲）未満ならレポート生成をスキップし、ループ全体もスキップ（投稿生成だけ単独で回らないようにする）
  3. Claude APIに分析を依頼し、以下を含む構造化レスポンスを得る:
     - 期間サマリー（投稿数・エンゲージメント集計）
     - 高評価/低評価だった投稿とその理由
     - 傾向（トピック・トーン・投稿時間帯など）
     - 次週への改善提案（`next_actions`）
  4. `weekly_reports` に保存
- **出力**: 保存されたレポートのレコード（`report_id` を含む）

### 5.2 ステップ③: プロンプト改善（既存 `analyzeAndImprove` の再構成）

現状の `analyzeAndImprove` は「データ分析」と「プロンプト改善」を1つのプロンプトで行っているが、これを以下のように分離する。

- **入力**: `accountId`, ステップ②で生成された `weekly_reports` レコード（`insights` + `next_actions`）
- **処理**:
  1. 現行の `system_prompt` / `reference_data` と、レポートの `insights` / `next_actions` をAIに渡す
  2. 「このレポートの提案を踏まえて、システムプロンプトと参考データをどう改善すべきか」を生成させる
  3. `prompt_configs` を upsert、`prompt_config_history` に履歴保存（既存ロジックを流用）
- **変更点**: 分析を再実行するのではなく、**既に保存済みのレポートを「読んで」改善する**という設計にすることで、要件の「分析レポートを読んだ上で次週のポストをつくる」を文字通り満たす。

### 5.3 ステップ④: 次週ポスト生成（既存 `/api/generate` のロジックを流用）

- 改善後の `prompt_configs` を使い、既存のClaude生成ロジックで7投稿を `draft` ステータスで生成
- 生成された投稿IDを `loop_runs.generated_post_ids` に記録

### 5.4 ループオーケストレーター（新規）

1サイクル分の②③④を連結して実行する関数（例: `runWeeklyLoop(accountId)`）を新設し、以下を担う。

1. `loop_runs` に `status='running'` のレコードを作成
2. ②レポート生成 → ③プロンプト改善 → ④投稿生成 を順次実行
3. 各ステップの結果を `loop_runs` に反映し、最終的に `status='completed'` または `'failed'` で更新
4. レポート生成がスキップされた場合はループ全体を `'completed'`（ただし投稿は生成しない）として記録し、その理由を残す

この関数はトリガー方式（手動ボタン / 将来のCron）に依存しないように設計し、`/api/loop/run`（手動トリガー用エンドポイント）から呼び出す。

## 6. UI / ダッシュボードへの影響

| 画面 | 変更内容 |
|---|---|
| アカウント詳細 or 新規「ループ」タブ | 「ループを1サイクル実行」ボタンを設置。実行状況（`loop_runs` の最新ステータス）を表示 |
| 分析（analytics）ページ | `weekly_reports` の一覧・詳細を表示。`insights` / `next_actions` / `metrics_summary` を人間が読める形で提示 |
| 投稿管理ページ | 既存の draft → review → ready フローはそのまま。生成元のループ実行（`loop_runs.id`）への参照リンクがあると追跡しやすい |

## 8. 将来の拡張（今回はスコープ外、設計のみ言及）

- **Cron化**: `runWeeklyLoop` はトリガー非依存のため、`/api/cron/weekly-loop` を追加するだけで自動化に移行可能。アカウントごとの実行曜日・時刻は `accounts.posting_times` に類する設定項目を別途追加して管理する想定
- **通知**: ループ完了時にメール等でレビュー依頼を送る機能。`loop_runs` の `status='completed'` への変化をトリガーに送信する設計が自然
- **品質スコアリング**: 生成された投稿を公開前にAIが事前評価し、低品質なものは自動再生成するなどの仕組み（自律度をさらに高める場合の次フェーズ）
